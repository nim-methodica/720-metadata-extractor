# זיהוי סוגי שאלות ומבנה answers/correctAnswers

לפי תקן 720, `questionType` הוא ערך יחיד מתוך: `fill-in` / `true-false` / `choice` /
`numeric` / `sequencing` / `matching` / `performance` / `other`. המבנה של `answers` ו-`correctAnswers`
משתנה לפי הסוג. מסמך זה מסביר איך לזהות כל סוג מהתסריט ואיך לכתוב אותו נכון.

**`{item-url}` בדוגמאות למטה** = ה-`id` המלא של הפריט (כולל ה-`/` בסוף), כפי שמתואר
ב-`conventions.md` תחת "פורמט ID". `questionId` = `{item-url}` + מספר השאלה (`q1`, `q2`...)
בלי מפריד נוסף — ראה גם `scripts/url_builder.py --question`.

## עקרון בסיסי

לפני שמזהים סוג, הסתכל בשקף:

1. **מה רואה הלומד?** שדה הקלדה חופשי? רשימת אפשרויות? גרירה?
2. **מה המקום הפיזי של התשובה במסך?** האם יש תבנית מולידה (`__ : 1`)?
3. **מה נדרש להזין?** מספר טהור? טקסט? רצף? זוגות?

## choice — שאלת בחירה מרובת אפשרויות

**זיהוי**: הלומד רואה 3-5 אפשרויות טקסטואליות ובוחר אחת (או יותר).

**מבנה**:
```json
{
  "questionId": "{item-url}q1",
  "questionType": "choice",
  "questionText": "נוסח השאלה",
  "answers": ["אפשרות א", "אפשרות ב", "אפשרות ג", "אפשרות ד"],
  "correctAnswers": ["אפשרות ב"]
}
```

- `answers` — כל האפשרויות המוצגות.
- `correctAnswers` — מערך של תשובות נכונות. יכול להיות יותר מאחת (בחירה מרובה).
- **הטקסט של התשובה בדיוק כפי שמופיע במסך** (כולל אות סעיף "א." "ב." אם יש).

## true-false — שאלת נכון/לא נכון

**זיהוי**: שתי אפשרויות בלבד — "נכון" ו"לא נכון" (או "כן" ו"לא").

**מבנה**:
```json
{
  "questionId": "{item-url}q1",
  "questionType": "true-false",
  "questionText": "טענה שיש לקבוע אם היא נכונה",
  "answers": ["נכון", "לא נכון"],
  "correctAnswers": ["נכון"]
}
```

## numeric — תשובה מספרית טהורה

**זיהוי**:
- הלומד רואה שדה הקלדה יחיד.
- התשובה היא **מספר בלבד** (אין ":1", אין ק"מ, אין יחידה).
- לרוב יש תבנית במסך שמראה את היחידה בקבוע (למשל שדה + "ס"מ", או שדה + ": 1").

**מבנה**:
```json
{
  "questionId": "{item-url}q1",
  "questionType": "numeric",
  "questionText": "נוסח השאלה",
  "answers": [],
  "correctAnswers": [25]
}
```

- `answers` תמיד `[]`.
- `correctAnswers` מכיל **מספר** (לא מחרוזת). כתוב `25000` ולא `"25,000"`.
- הפלטפורמה תזהה אוטומטית `25000` וגם `25,000` כי היא משווה ערך מספרי.

**דוגמאות**:
- "מהי המסה בגרם?" → `25` (מספר)
- "חשבו את קנה המידה: __ : 1" → `25000` (המספר בלבד; ה-":1" קבוע במסך)
- "כמה מטרים?" → `4` (מספר)

## fill-in — תשובה מחרוזתית

**זיהוי**:
- הלומד מקליד טקסט חופשי (או מחרוזת מורכבת).
- התשובה **אינה מספר טהור** — כוללת מילים, יחידות, סמלים כמו ":1".
- אין תבנית קבועה במסך שמפרידה את המספר מהטקסט.

**מבנה**:
```json
{
  "questionId": "{item-url}q1",
  "questionType": "fill-in",
  "questionText": "נוסח השאלה",
  "answers": [],
  "correctAnswers": [
    "25,000 : 1",
    "25,000:1",
    "25000 : 1",
    "25000:1"
  ]
}
```

- `answers` תמיד `[]`.
- `correctAnswers` מכיל **מחרוזות**. אם תשובה יכולה להיכתב בואריאנטים שונים (עם/בלי פסיק,
  עם/בלי רווח סביב הנקודתיים) — הוסף כמה ואריאנטים. **יחס (a:b) נכתב בסדר לוגי ובלי רווחים**
  (הוריאנט הראשון `4:3`) — ראה conventions.md, "כתיבת יחסים".

## sequencing — סידור פריטים לפי סדר

**זיהוי**: הלומד גורר פריטים כדי לסדר אותם בסדר נכון. יש 3-6 פריטים עם מספרים 1, 2, 3...

**מבנה**:
```json
{
  "questionId": "{item-url}q1",
  "questionType": "sequencing",
  "questionText": "סדרו את שלבי X לפי הסדר",
  "answers": [
    "שלב א",
    "שלב ב",
    "שלב ג",
    "שלב ד"
  ],
  "correctAnswers": [
    "שלב א",
    "שלב ב",
    "שלב ג",
    "שלב ד"
  ]
}
```

- `answers` — כל הפריטים שנתונים ללומד (כולל כאלו שלא צריכים להיכלל בפתרון, אם הפריט
  דורש סינון).
- `correctAnswers` — הפריטים בסדר הנכון (בלי הפריטים שאמורים להישלף).

## matching — התאמה בין שני קבוצות

**זיהוי**: הלומד **גורר** פריטים מקבוצה אחת לקבוצה אחרת (drag & drop אמיתי בין מקור
ליעד), **או** שאלה עם **כמה תפריטים נפתחים (dropdown) שכולם מציעים את אותן אפשרויות
בדיוק** (רשימה נפתחת זהה בכל התפריטים).

**⚠️ עדכון (2026-10-14) — dropdown לפי כמות ותוכן הרשימות** (מחליף את הכלל הישן "גם dropdown
בודד = matching"):

| מצב בשקף | `questionType` |
|---|---|
| **dropdown יחיד** (תפריט נפתח אחד) | `choice` — **לא** `matching` |
| **dropdown מרובים, אותה רשימה נפתחת בכולם** | `matching` |
| **dropdown מרובים, רשימות נפתחות שונות** (לכל תפריט אפשרויות משלו) | `performance` — ראה "performance" למטה |

בדיקה: אם יש יותר מתפריט אחד — השווה את קבוצת האפשרויות של כל התפריטים (בלי תלות בסדר).
זהות מלאה → `matching`; שונה אפילו באפשרות אחת → `performance`.

**⚠️ עדכון (2026-09-08) — בוטל**: לא לסווג כ-matching שאלה עם **כמה שדות הקלדת טקסט/
מספר נפרדים** באותו סעיף (למשל "מדדו 3 פעמים ורשמו כל תוצאה", או טבלה עם כמה תאים
ריקים למילוי אחוזים/ערכים). זו **הזנת טקסט**, לא גרירה — ראה "שדות הקלדה מרובים באותו
סעיף" למטה. (עד עכשיו הכלל כאן כלל בטעות גם את המקרה הזה בתוך matching — תוקן ואומת
מול המשתמש.)

**מבנה**:
```json
{
  "questionId": "{item-url}q1",
  "questionType": "matching",
  "questionText": "גררו את X ל-Y",
  "answers": {
    "source": ["פריט א מקבוצת מקור", "פריט ב", "פריט ג"],
    "target": ["ערך 1", "ערך 2", "ערך 3", "ערך 4"]
  },
  "correctAnswers": [
    {"source": "פריט א מקבוצת מקור", "target": "ערך 2"},
    {"source": "פריט ב", "target": "ערך 4"},
    {"source": "פריט ג", "target": "ערך 1"}
  ]
}
```

- `source` — הפריטים שצריך למצוא להם התאמה.
- `target` — האפשרויות שאפשר לגרור אליהן.
- `correctAnswers` — מערך של אובייקטים עם זוגות `{source, target}`.

**אין חובה שכל source יתאים ל-target (אפשר להשאיר בלי התאמה) — לפי התקן**.

**⚠️ מקורות שהם תמונות/גרפיקה (למשל: "גררו תיאור מתאים ל-4 מטרות קליעה", גרפים, סדרות
מדידה מוצגות כתמונה) — עצור ושאל את המשתמש, אל תנחש.**

`source` חייב להכיל את **המזהה הנקי** בלבד, כפי שהוא מופיע כטקסט בשקף (למשל: `"מטרה 1"`,
`"מטרה 2"`, `"סדרה 1"`) — **לעולם אל תשתול לתוכו פרשנות ויזואלית מנוחשת** (לא `"מטרה 1 -
חיצים מפוזרים סביב המרכז"`). הפרשנות של מה מוצג בכל תמונה שייכת אך ורק ל-`correctAnswers`,
ורק אם אפשר לקבוע אותה בוודאות מהטקסט שחולץ.

אם **התוכן שקובע את הזיווג הנכון (`correctAnswers`) מופיע רק בתמונה/גרף/דיאגרמה ואין לו
תיאור טקסטואלי מקביל** ב-`slides.txt` — זה בדיוק המקרה היחיד שבו אסור להמשיך לבד:
1. **עצור** את העיבוד של הפריט הזה.
2. **תאר למשתמש** בדיוק מה חסר (למשל: "בפריט X יש שאלת matching בין 4 'מטרות קליעה' —
   התמונות לא מכילות תיאור טקסטואלי של הדפוס בכל מטרה. מה מוצג בכל אחת, ומה הזיווג
   הנכון ל-4 היעדים?").
3. **המתן לתשובת המשתמש** ומלא את `correctAnswers` לפיה.

**אסור**:
- לנחש פרשנות ויזואלית סבירה-אך-לא-מאומתת ולהציג אותה כעובדה.
- להשאיר `correctAnswers: []` ולהמשיך הלאה בלי לשאול — הפלט הסופי חייב להיות מלא.

זהו יוצא הדופן היחיד לעיקרון "אפס שאלות למשתמש" של הסקיל — ראה `conventions.md`.

## performance — ביצוע רב-שלבי (עדכון 2026-10-14, הורחב 2026-10-15)

**זיהוי** (סעיף אחד, כמה "שלבים"/שדות), אחד משניים:
1. **כמה dropdown עם רשימות נפתחות שונות** בין התפריטים (לכל פער/תא אפשרויות משלו). רשימה
   זהה בכולם → `matching`; תפריט יחיד → `choice`.
2. **כמה תיבות הקלדה** באותו סעיף (ראה "שדות הקלדה מרובים באותו סעיף" למטה). בשלב כזה אין
   `options` — רק `step`.

**מבנה לפי טופס ההזנה במערכת (צילום מסך, 2026-10-15)**: בטופס, `performance` = מזהה שאלה,
נוסח השאלה, ורשימת **"שלבים (לפי הסדר)"**. לכל שלב: **שם שלב** (בצילום המערכת מופיע שם
ברירת-מחדל `s1`, `s2`, `s3`), **סוג — `טקסט` או `טווח מספרי`**, ו"תשובה צפויה": לטקסט —
שדה תשובה יחיד; לטווח מספרי — `מ-` ו-`עד`.

- **⚠️ שם השלב = תיאור התיבה כפי שהיא מוצגת ללומד, לא `s1`/`s2`** (עדכון 2026-10-15) —
  למשל `מונה`, `מכנה`, `סמ"ק`, `מספר גלידות`, `חנקן`. לוקחים את התווית/היחידה/ההקשר שליד
  התיבה בשקף. לא להשאיר `s1..sN` כשם. אם אין לתיבה תווית ברורה בשקף — נסח תיאור קצר מההקשר
  (נוסח השאלה/העמודה/השורה), ואל תמציא מושג שלא מופיע.
- מספר השלבים = מספר התיבות בשקף, לפי סדר הופעתן.
- תיבת הקלדה של **טקסט** → סוג `טקסט` + התשובה הצפויה; תיבה שהתשובה בה **מספר** →
  `טווח מספרי`, ו-`מ-`/`עד` = אותו מספר אם התשובה מדויקת, או הגבולות המותרים אם יש טווח
  קבלה (לפי השקף / `script.js`; לא להמציא טווח).

```json
{
  "questionId": "{item-url}q1",
  "questionType": "performance",
  "questionText": "נוסח השאלה",
  "steps": [
    {"name": "מספר גלידות", "type": "numeric-range", "min": 12, "max": 12},
    {"name": "נפח בסמ\"ק", "type": "numeric-range", "min": 49.5, "max": 50.5},
    {"name": "חומר", "type": "text", "correctAnswer": "חנקן"}
  ]
}
```

- **⚠️ שמות השדות ב-JSON (`steps`, `name`, `type`, `min`, `max`, `correctAnswer`) הם ניחוש שלי**
  על סמך הטופס — הטופס מראה רק את מה שמוזן בו, לא את פורמט ה-JSON/ה-API. לפני שימוש
  ב-`send-metadata`/בקובץ סופי יש לאמת מול דוגמת `performance` קיימת בפלטפורמה (או מול המפתחים).
- הטופס מציע לשלב רק `טקסט` / `טווח מספרי` — אין שלב מסוג dropdown. **לכן כל dropdown
  בתוך `performance` (מרובים עם רשימות שונות) מוזן כשלב מסוג `טקסט`** (עדכון 2026-10-15):
  `name` = תיאור התפריט/הפער, `correctAnswer` = טקסט האפשרות הנכונה בדיוק כפי שמוצגת ברשימה.
  שאר האפשרויות ברשימה לא נרשמות בשלב (אין להן מקום בטופס).

  ```json
  {"name": "כיוון התנועה", "type": "text", "correctAnswer": "עולה"}
  ```
  (המבנה והשמות ב-JSON עדיין לאימות מול הפלטפורמה — ראה האזהרה למעלה.)
- **הערה**: `performance` אינו ברשימה הסגורה של `standard.md` — יש לאמת גם את שם הערך.

## other — כל השאר

אם השאלה לא נופלת באחת מהקטגוריות למעלה (למשל: ציור, הקלטה, בחירת כפתור באנימציה),
השתמש ב-`other`. נסה קודם לזהות אם באמת אין התאמה — הרוב הגדול נופל תחת הקטגוריות
הרגילות.

## שאלות "ללא מענה מוערך" (Selected במקום Answered)

חלק מהפריטים אינם דורשים תשובה מוערכת אלא רק **בחירה** של הלומד (בחירת דמות, בחירה בין
פלייליסטים, בחירת מצב לימוד). לפי תקן xAPI זו פעולה מסוג `Selected` ולא `Answered`.

**איך לרשום במטא-דאטה של הפריט:**
- אם אין שאלה כלל (רק בחירה טכנית): `"questions": []`.
- אם יש בחירה שהיא חלק מרצף מוערך (חימום כלשהו): רשום אותה כשאלה רגילה עם `choice`.

## שאלות עם סעיפים מרובים

פריט אחד יכול להכיל 2, 3, או 4 סעיפים (א', ב', ג', ד') — כל אחד כשאלה נפרדת ב-
`questions[]`. סמן את סיומת מזהי השאלות `q1, q2, q3, q4` (מודבקת ל-`{item-url}`, ראה למעלה)
ואת נוסח השאלה עם הסעיף:

```json
"questions": [
  {
    "questionId": "{item-url}q1",
    "questionText": "א. חשבו X",
    ...
  },
  {
    "questionId": "{item-url}q2",
    "questionText": "ב. חשבו Y",
    ...
  }
]
```

## שדות הקלדה מרובים באותו סעיף (עדכון 2026-09-08)

**⚠️ אל תבלבל עם "שאלות עם סעיפים מרובים" למעלה.** ההבדל:
- **סעיפים מרובים** (א/ב/ג עם נוסח נפרד לכל אחד) → כמה **שאלות נפרדות** ב-`questions[]`
  (q1, q2, q3...), כל אחת עם `questionId`/`questionText`/`correctAnswers` משלה.
- **כמה תיבות הקלדה באותו סעיף** (למשל "מדדו 3 פעמים ורשמו כל תוצאה", או טבלה/תרשים
  עם כמה תאים ריקים למילוי — כמו גרף עוגה עם 4 אחוזים חסרים). זה **לא** matching (אין
  גרירה בין מקור ליעד) — זו הזנת טקסט/מספר; ראה למטה איך לתייג.

**⚠️ עדכון (2026-10-14) — הכלל הקודם בוטל**: תיוג שאלה מרובת תיבות/סעיפים כ-`fill-in` יחיד
עם `correctAnswers` שהוא **מחרוזת חופשית אחת** שמרכזת ברצף, מופרדת בפסיקים, את כל התשובות
(למשל `"חנקן: 78%, חמצן: 21%, ..."`) — **זו אינה הדרך הנכונה לתייג. אסור.**

**איך לרשום עכשיו (עדכון 2026-10-15)**: שאלה אחת עם **כמה תיבות הקלדה** היא
**`performance`** (ביצוע רב-שלבי) — שאלה **אחת** (`questionId`/`questionText` יחידים), כשכל
תיבה היא "שלב" ב-`answers` וב-`correctAnswers`. מבנה: ראה "performance" למעלה (לתיבת הקלדה
אין `options` — רק `step`). **לא** לפצל לשאלות נפרדות ו**לא** מחרוזת מופרדת בפסיקים.
כל שלב נקרא בתיאור התיבה (`name`: למשל "חנקן"), לא `s1..sN` (ראה מבנה למעלה).

```json
{
  "questionId": "{item-url}q1",
  "questionType": "performance",
  "questionText": "שחזרו את אחוזי הגזים החסרים בגרף העוגה של הרכב האוויר.",
```
